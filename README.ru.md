# Universal Character Card Exporter

[English](README.md) · [Español](README.es.md) · [日本語](README.ja.md) · [Italiano](README.it.md) · [Deutsch](README.de.md) · **Русский**

Расширение для браузера, которое читает персонажа с **JanitorAI**, **Emochi**, **Polybuzz**, **Character.ai** или **Crushon.ai** и сохраняет его как переносимую карточку персонажа — для резервной копии или переноса на другой фронтенд. Без аккаунта, без сборки, без сервера. Работает в вашем браузере, под вашей сессией.

**Новое в 0.9.0:** читатели Character.ai и Crushon.ai, примеры диалогов Polybuzz, парсер Emochi, который перестал терять поля, и Emochi Lab. Подробности в [changelog](CHANGELOG.md) и в [devlog](#devlog).

> Бесплатно и с открытым кодом. Если пригодилось и хочется поддержать исходную работу — загляните на [inkwell.rip](https://inkwell.rip). Именно это позволяет таким инструментам существовать.

## Как инструмент устроен

Расширение — это четыре небольшие части, у каждой одна задача, и одно правило, которое держит всё вместе: **каждый читатель сайта выдаёт один и тот же объект карточки**.

```
страница сайта
   │
   ├─ src/scraper.js    читает JanitorAI
   ├─ src/emochi.js     читает Emochi (страницы персонажей и Lab)
   ├─ src/polybuzz.js   читает Polybuzz
   ├─ src/cai.js        читает Character.ai
   ├─ src/crushon.js    читает Crushon.ai
   │       ▲
   │       └─ src/intercept.js + src/harvest.js
   │          (сайты, отдающие запись только своему клиенту)
           │
           ▼
     один объект карточки
     { name, creator, avatarUrl, gender, tags,
       fields: { description, personality, scenario,
                 greeting, altGreetings, exampleDialogue },
       lorebooks[], scriptRefs[] }
           │
           ├─ src/exporters.js  ──▶ .card.json / .card.png / .lorebook.json / .jai.json / .txt
           └─ src/panel.js      ──▶ интерфейс на странице: список блоков, флажки, экспорт
```

1. **Чтение.** Читатель того сайта, где вы находитесь, собирает персонажа. Каждый делает это по-своему, потому что у каждого сайта своя поверхность: у JanitorAI внутренний JSON API, у Emochi бэкенд на Next.js с компилированным промптом, у Polybuzz отрендеренная на сервере полезная нагрузка Nuxt плюс REST API, а Character.ai и Crushon.ai отдают запись только своей собственной странице — там расширение перехватывает то, что страница уже загрузила, вместо того чтобы спрашивать самому.
2. **Нормализация.** Сырая запись разворачивается в объект карточки. Здесь же переводятся имена полей: `sceneBrief` из Polybuzz становится `description`, `speechText` — `greeting`, `templateIntro` — `scenario`. Ничего не выдумывается. Если поле не опубликовано, оно остаётся пустым.
3. **Показ.** Панель перечисляет найденные блоки с флажком и превью, чтобы можно было убрать попавшую в карточку строку джейлбрейка или системный промпт. Счётчик сверху (`x/y kept`) точно говорит, что будет записано.
4. **Экспорт.** `toBlocks()` превращает отмеченные блоки в нужный формат. Экспортёр не знает сайтов: он никогда не слышал ни про Emochi, ни про Polybuzz, он знает только объект карточки. Поэтому каждый сайт получает все пять форматов бесплатно.
5. **Сохранение.** Создаётся Blob и нажимается через `<a download>`. Сеть не задействована.

В `toBlocks()` есть намеренная защита: если блок Personality оказывается посимвольно равен блоку Description, он молча отбрасывается. Почти всегда это сервер, переливающий одно поле в другое, а не автор, дважды написавший один и тот же абзац.

### Почему расширение, а не сайт

Каждый из этих сайтов держит хотя бы часть данных за авторизованной сессией. Веб-приложению понадобились бы ваши cookie; расширение может одолжить сессию, которая уже есть у браузера, и никогда не видит ваш пароль. В этом вся причина, почему инструмент живёт там, где живёт.

## Установка (около двух минут)

Программировать не нужно. Собирать и компилировать нечего.

1. **Скачайте проект.** Зелёная кнопка **Code** на странице GitHub, затем **Download ZIP**. Распакуйте в постоянное место, например на рабочий стол.
2. **Откройте страницу расширений.** Chrome: `chrome://extensions`. Edge: `edge://extensions`.
3. **Включите режим разработчика** (переключатель справа сверху).
4. Нажмите **Load unpacked** / **Загрузить распакованное** и выберите папку, в которой лежит `manifest.json`.

> Если переместить или удалить эту папку, расширение перестанет работать. Держите её на постоянном месте.

## Использование

### JanitorAI

1. Откройте персонажа на [janitorai.com](https://janitorai.com), будучи авторизованным.
2. Нажмите **Extract card** в правом нижнем углу.
3. **Quick scan** читает персонажа. **Deep scan** дополнительно обходит все привязанные лорбуки — медленнее, полнее.
4. Снимите галочки с ненужного. **Select all** / **Select none** для этого и есть.
5. Выберите формат экспорта.

Если у персонажа больше одного лорбука, после глубокого сканирования появляется кнопка **Separate books** — чтобы общий мир-лорбук сохранился отдельным переиспользуемым файлом.

### Emochi

1. Откройте персонажа на [emochi.com](https://emochi.com) (`emochi.com/character/...`).
2. **Quick scan** читает публичную нагрузку: имя, слоган/описание, приветственное сообщение, теги, аватар, автора.
3. **Deep scan** дополнительно запрашивает определение автора: личность, сценарий, примеры диалогов. Этот маршрут отвечает только для персонажей **вашего аккаунта**; сначала войдите.

У части персонажей Emochi действительно нигде не сохранён текст личности или сценария: сайт ведёт их тегами и генерирует персону в момент чата. Это свойство персонажа, а не сбой чтения.

### Polybuzz

1. Откройте персонажа на [polybuzz.ai](https://polybuzz.ai) (`polybuzz.ai/es/character/chat/...`).
2. **Extract card** → **Quick scan**.
3. Экспорт.

Карточка Polybuzz содержит то, что сайт публикует:

| Поле карточки | Источник в Polybuzz |
|---|---|
| Description | `sceneBrief` — короткое вступление |
| Greeting | `speechText` — начальное сообщение |
| Scenario | `templateIntro`, если бот шаблонный; иначе ремарка, которую автор написал в начале приветствия |
| Personality | теги **Personalidad**, выбранные самим автором (`Frío`, `Celoso`, `Tsundere`…), плюс стиль диалога, если он опубликован |
| Gender | `sceneGender`, как строка `Gender: Male/Female/Non-binary` в описании |
| Теги, аватар, имя, автор | запись сцены |

### Character.ai

1. Откройте персонажа на [character.ai](https://character.ai) с активной сессией (`character.ai/character/...`).
2. Дождитесь загрузки страницы, затем **Extract card** → **Quick scan**.
3. Экспортируйте.

| Поле карточки | Источник в Character.ai |
|---|---|
| Имя, автор, аватар | запись персонажа |
| Description | `title` (слоган), затем `description` (текст «About») |
| Greeting | `greeting` |
| Пример диалога | `definition` — свободный текст определения от автора, если он публичный |

**Об определении.** Character.ai прячет определение персонажа за вторым переключателем автора — **Definition Visibility**, отдельным от видимости персонажа. Когда он выключен, сайт не отправляет текст никому, поэтому блок примера диалога выходит пустым, и панель говорит об этом в сноске. Остальные поля есть независимо от него.

Читатель работает, наблюдая за запросами самой страницы: небольшой скрипт в мире страницы (`src/intercept.js`) копирует заголовок `Authorization` в скрытый тег и переотправляет каждый JSON-ответ как событие DOM, откуда его забирает читатель. Он никогда не изменяет запрос и не отправляет свой с вашим токеном. Когда страница ещё не сделала вызов, читатель повторяет те же три эндпоинта, что использует сайт, через service worker расширения.

### Crushon.ai

1. Откройте персонажа на [crushon.ai](https://crushon.ai) (`crushon.ai/character/...`).
2. Дождитесь загрузки страницы, затем **Extract card** → **Quick scan**.
3. Экспортируйте.

Crushon полностью рендерится на клиенте, поэтому читатель берёт запись, которую страница уже отрисовала, вместо вызова API. Псевдонимы полей покрывают все написания, которые сайт использовал между релизами: `firstMessage` / `first_mes` / `greeting`, `description` / `introduction` / `intro`, `avatar` / `avatarUrl` / `image`, `mes_example` / `exampleDialogue` / `dialogue`. Если страница ещё не запросила персонажа, перезагрузите её и просканируйте снова.

**О названиях полей.** Импортёр Crushon отображает карточку Tavern в обратном порядке: `personality` карточки становится *Introduction* в Crushon, а `description` карточки становится *Personality* в Crushon. Читатель записывает то, что публикует Crushon, в то поле карточки, которое означает то же самое, — поэтому проход через оба инструмента оставляет текст там, где он был.

## Polybuzz: информацию о предыстории получить нельзя. Вот почему.

Руководство по созданию в Polybuzz перечисляет семь составляющих персонажа: имя, пол, короткое вступление, приветствие, теги, **предысторию** и **стиль диалога** (плюс пример диалога, задающий стиль). Публичная страница отдаёт пять. Остальные две — `systemRole` (предыстория, обозначена как *Antecedentes*) и `conversationExample` (примеры диалогов) — **не отправляются никому, кроме автора этого персонажа**. Это не недостающий эндпоинт и не то, что можно обойти этим или любым другим расширением, потому что **данные собираются на сервере и никогда не сериализуются для не-владельца**.

Доказательства, кратко:

- Сама форма создания показывает поле как `Antecedentes (Visto en privado)` — *Antecedentes, видно только приватно*. Это заметка только для автора, по замыслу.
- Все маршруты API только для чтения, которые знает веб-клиент, были вызваны к публичным ботам со свежей гостевой сессией. Единственный, где вообще есть этот ключ, — `scene/detailguest`, и он возвращает `""`.
- Маршрут владельца `scene/getscenedetail` отвечает `210002` на бота, которым ваш аккаунт не владеет. Этот код окончателен: сервер отказывает в записи.
- Во всех 225 лениво загружаемых JavaScript-чанках сайта `systemRole` и `conversationExample` встречаются в **одном** файле — на странице создания. Ни одна другая страница их не запрашивает, значит, ни одна не может их показать.
- Контрольный эксперимент закрывает вопрос: бот, у которого в Antecedentes стоит метка `ZZZ-123`, просканированный со второго аккаунта, метку не показал ни разу. Значение не покидает сессию автора.
- Попросить модель процитировать собственные инструкции тоже не работает. Конвейер чата собирает системный промпт на сервере, а поток несёт только текстовые фрагменты. Когда у бота спросили его биографию, он уверенно выдумал детство, которого не было. Пересказ — не сохранённый текст, и это расширение не выдаёт генерацию за извлечение.

**Что расширение делает вместо этого:** использует поля, которые Polybuzz действительно публикует, и говорит об этом в сноске под списком блоков. Personality берётся из тегов, выбранных автором; Scenario — из начальной ремарки приветствия, дословно. Ничего не пересказывается и не выдумывается.

Если персонаж ваш, все три авторизованных маршрута по-прежнему опрашиваются при каждом сканировании, и ваши боты возвращаются полностью.

## Как этот форк создавался, от начала до конца

Короткая запись: форма процесса объясняет, почему ограничения выше заслуживают доверия.

1. **Начать с исходного инструмента.** Апстрим-расширение уже читало JanitorAI. Оно стало базой, и правило для всего дальнейшего было: никогда не менять унаследованное поведение, только добавлять рядом.
2. **Добавить читатель, а не особый случай.** Emochi добавлен как `src/emochi.js`, заполняющий тот же объект карточки, поэтому `exporters.js` и `panel.js` не потребовали изменений вообще.
3. **Найти настоящую нагрузку.** Emochi — приложение Next.js на бэкенде FlowGPT; полезные данные лежат в скомпилированной строке `initPrompt` внутри публичного объекта промпта. Эта строка разбирается обратно на личность, предысторию, сценарий и пример диалога.
4. **Измерять, а не предполагать.** Утверждение, что Emochi публикует определение примерно для трети персонажей, получено на трёх независимых живых выборках (30, 19 и 9 персонажей) с подсчётом. Это флаг публикации (`visibility: true`), а не входной барьер.
5. **Добавить Polybuzz так же.** Nuxt рендерит персонажа на сервере прямо в страницу, поэтому нагрузка лежит в DOM как массив devalue. Этот массив разворачивается и обыскивается. Content script не видит `window.__NUXT__`, поэтому используется тег `<script id="__NUXT_DATA__">`.
6. **Перечислить API, а не угадывать его.** JavaScript-бандл сайта объявляет 214 конфигураций запросов. Все доступные только для чтения были вызваны к публичным ботам. Так и получен вывод «предыстория недостижима» — не одним провалом, а исчерпанием поверхности.
7. **Доказать отрицание контролем.** Эксперимент с `ZZZ-123` на двух аккаунтах превратил «мы не находим» в «этого там нет, чтобы найти».
8. **Держать панель молчащей.** Отсутствующее приватное поле автора — норма, а не ошибка. Панель показывает сноску, а не баннер. Сообщение получает только настоящий сбой (не выполнен вход, ни один маршрут не ответил).
9. **Тестировать всё, что тестируется.** `node --test` покрывает читатели, нормализатор, экспортёры и сборщик блоков. 71 тест на момент написания. Каждое утверждение об API в этом README проверено на живом сайте, а непроверяемые помечены как таковые.
10. **Записать.** Раздел для разработчиков существует, чтобы следующему человеку не пришлось выводить всё заново.
11. **Сначала переиспользовать, потом писать.** Character.ai и Crushon.ai отдают запись только своему JavaScript, поэтому один механизм покрывает оба: сниффер в мире страницы и проход с оценкой по нагрузкам. По одному новому файлу на сайт, два общих — и экспортёры не тронуты.
12. **Указывать источник подхода.** Схема перехвата взята из [экспортёра taquanta](https://github.com/taquanta/character-ai-to-crushon-ai-card-exporter), и упоминание стоит в начале файла и в этом README, а не только в сообщении коммита.
13. **Говорить, что не проверено.** Оба новых сайта отвечают `403` от Cloudflare машине без браузера, поэтому контракты задокументированы, а живое чтение — нет. Это написано в трёх местах вместо того, чтобы быть обойдённым.

**Инструмент активно развивается и будет получать обновления.** Добавляются сайты, чинятся сломанные читатели, заметки по API правятся, когда сайт меняется. Если что-то сломалось, обычно это значит, что сайт изменил форму нагрузки, — и это исправимо.

### 0.9.0 — два закрытых сайта, один механизм и парсер Emochi с тремя ошибками

**Сначала Emochi, потому что это был приоритет.** Открытыми были два сообщения: отсутствие личности и сценария у части ботов и `characterExampleConversation`, который так и не доходил до карточки.

Ошибка с примерами диалогов заняла десять минут. Маршрут определения возвращает `characterExampleConversation` как **массив ходов**, а читатель применял к нему `String(...)`. Массив превращается в `"[object Object],[object Object]"` в одних средах и в `""` в хелпере `s()` нормализатора — в любом случае это не диалог. Теперь он разбирается как ходы, и парсер принимает `{role, content}`, `{user, ai}`, `{isUser, text}` и обёртку `{dialogue: [...]}`, потому что собственный рекордер Emochi использует первую форму, импортёры карточек — вторую, а остальные встречаются в записях до смены схемы.

Ошибка с личностью заняла больше времени и оказалась тремя наложенными дефектами:

1. **Закрывающая инструкция считалась границей.** Каждый скомпилированный промпт заканчивается строкой `Do not write as {{user}} or assume {{user}}'s reaction or response.` Читатель обрезал текст там и выбрасывал весь хвост. Это правильно для промпта, который заканчивается правилом, — то есть для того, что создаёт компилятор. Это неправильно в тот момент, когда автор цитирует правило внутри своей предыстории или своего примера диалога, а случается это чаще, чем кажется: люди намеренно вставляют правило в свой пример, чтобы научить модель. Каждая секция после цитаты исчезала. Исправление — убирать это предложение там, где оно встречается, и сохранять текст вокруг.
2. **Грамматика секций принимала ровно одно написание.** Маркерами были `'s personality:`, `'s background:`, `scenario of role-play:`. Автор, написавший `Personality:` — с заглавной, без притяжательного, потому что писал свой промпт вместо конструктора, — получал пустой разбор, и весь промпт уходил в ветку «маркеров нет, считай это личностью». Теперь есть второй набор маркеров, привязанный к началу строки и терпящий отклонения, и побеждает проход, распознавший больше секций. При равенстве остаётся строгая грамматика, поэтому промпты компилятора разбираются точно как раньше.
3. **Примечание о пустых секциях было догадкой.** Читатель сообщал «автор оставил личность и пример диалога пустыми» всякий раз, когда эти поля выходили пустыми — включая случаи, когда парсер вообще не распознал разметку, и поля были пустыми из-за парсера. Теперь примечание срабатывает только когда распознана и строка имени, то есть разметка действительно понята.

Все три покрыты тестами, написанными из падающих форм, а не из проходящих.

**Затем примеры диалогов Polybuzz.** В тикете был скриншот редактора *Estilo de diálogo*: строки с аватаром рядом — это `{{user}}`, строки без — `{{char}}`. Чтение бандла страницы создания подтвердило форму: `dialogueStyleObj` — массив пар `{user, ai}`, по одной на обмен, а запись деталей возвращает его под `dialogueStyle.dialogue`. Оба теперь разбираются в строки карточки. Плоская строка `conversationExample` — те же данные как `user;ai` на строку, и эта форма тоже переписывается.

Одна ловушка: простая строка под `dialogueStyle` — это **метка стиля** (`Descriptivo, frases cortas`), а не диалог. Первая версия парсера бодро переписала метку стиля в `{{char}}: Descriptivo, frases cortas` и положила её в блок примеров. Тесты поймали. Теперь строки никогда не становятся диалогом; только массивы и текст `user;ai`.

**Затем Character.ai.** Подход взят из [экспортёра taquanta](https://github.com/taquanta/character-ai-to-crushon-ai-card-exporter), который решил ту же задачу: запись запрашивает только JavaScript самой страницы, с заголовком `Authorization: Token <hex>`, который расширение не может выписать. Референсная реализация запускает скрипт в мире страницы (`MAIN`), перехватывает `fetch` и `XMLHttpRequest` и сохраняет заголовок в DOM. Это единственный способ увидеть заголовок, который браузер добавляет вне вашего контекста.

Два изменения. Токен попадает в мета-тег с собственным пространством имён вместо того, который может столкнуться. И каждый JSON-ответ, который получает страница, переотправляется как событие DOM, несущее **строку**, — объекты не пересекают границу между скриптом `MAIN` и изолированным content script, а строки пересекают. Это единственное изменение превратило сниффер из «поймай токен и повтори вызов» в «поймай токен *и* ответ», поэтому читатель продолжает работать, когда повтор отклонён.

Определение — интересное поле. Character.ai прячет его за **Definition Visibility**, вторым переключателем, отдельным от видимости персонажа, и когда он выключен, текст не отправляется никому. Поэтому карточка с пустым блоком примера диалога — это настройка автора, а не неудачное чтение, и панель говорит именно это вместо показа ошибки.

**Затем Crushon.ai.** Полностью рендерится на клиенте, за стеной защиты от ботов. Публичного API для повтора нет, а вызовы страницы несут состояние сессии, поэтому читатель ничего не вызывает: он проходит по нагрузкам, которые страница уже получила, и оценивает каждый объект по числу известных имён полей. Побеждает самый богатый. Псевдонимы покрывают написания, которые сайт использовал между релизами, потому что пропущенное написание стоит целого поля.

Общая часть обоих читателей — `src/harvest.js`: сбор нагрузок, перечитывание токена и проход с оценкой. Два новых читателя, два общих файла, ноль изменений в `exporters.js` или `panel.js` — правило, что каждый читатель заполняет один и тот же объект карточки, сделало это возможным, и оно же означает, что следующий сайт стоит одного файла.

**Что не удалось проверить.** Оба новых хоста отвечают `403` от Cloudflare машине, на которой это собиралось, поэтому ни один из читателей не проверялся против браузера с сессией. Что проверено: эндпоинт neo жив и отвечает `{"status":"NOT_OK","error":"bad request"}` на синтетический идентификатор — то есть маршрут ругается на тело, а не на вызывающего. Контракты полей взяты из работающей реализации taquanta. Это записано как непроверенное в changelog, в планах и здесь, потому что не запускавшийся читатель — это другое утверждение, чем запускавшийся.

### 0.8.0 — у форка появляется имя и шесть языков

Репозиторий всё ещё носил исходное имя, поддерживая четыре сайта. Переименован в **Universal Character Card Exporter** — это то, что он делает. Issues включён тогда же, потому что раздел о сообщениях об ошибках отправлял людей во вкладку, которой не существовало.

Документация переведена на шесть языков за один проход. Справочник по API для каждого сайта остаётся на английском и говорит об этом в начале раздела: это справочный материал, который устаревает быстрее всего, а шесть копий устаревшего документа — это шестикратное обслуживание без выгоды. Переводы ссылаются туда.

Раздел Polybuzz переписан. Раньше там был вывод «получить нельзя». Теперь под ним лежат доказательства — метка приватности по замыслу в форме создания, исчерпывающий обход маршрутов, `210002` на чужом боте, контрольный тест `ZZZ-123` на двух аккаунтах. Утверждённый отрицательный результат не стоит ничего; отрицательный результат с приложенным методом стоит чего-то.

### 0.7.13 — личность из тегов самого автора

Polybuzz не публикует ни предысторию, ни поле личности, из-за чего блок Personality в карточках оставался пустым. Дерево тегов уже запрашивалось для списка тегов карточки, поэтому его прочитали внимательнее: каждый тег лежит под одним из четырёх родителей, а `Personalidad` содержит 41 слово темперамента, которые автор выбирает вручную. Это характеристика автора, написанная им, опубликованная сайтом.

Соединение честно в конкретном смысле: теги жанра, происхождения и идентичности остаются вне Personality и в списке тегов, а настоящий `systemRole` по-прежнему важнее тегов, когда он есть. Измерено на 10 живых ботах: 10/10 дали настоящий блок Personality. Список тегов тоньше написанной предыстории, но это слова автора, а не догадка.

### 0.7.10 – 0.7.12 — эхо это не поле

Три релиза, одна идея. `getsceneconfig` с идентификатором сцены отвечает скомпилированным текстом вступления как запасным вариантом. Пять авторизованных сканирований ботов, которыми аккаунт не владеет, вернули `systemRole`, посимвольно совпадающий с `sceneBrief`. Так сервер рендерит пустую предысторию, а не второе поле, которое случайно совпало. Точное эхо теперь считается отсутствием, каждый маршрут сохраняет свой ответ вместо первого непустого, а панель показывает сноску вместо баннера, потому что приватное поле автора — это норма.

Сценарий вышел из той же работы: приветствия Polybuzz часто начинаются с ремарки (`*Bangchan es tu esposo*`), а это предпосылка самого автора. Она переносится дословно, когда в записи нет `templateIntro`. Пересказа не бывает никогда.

## Это разрешено?

Это инструмент личного резервного копирования. Он читает то, что вы и так видите авторизованным, и сохраняет это в открытом формате. Он не обходит платные стены и не открывает ничего, чего вы не могли бы увидеть.

Условия сайтов могут всё же ограничивать автоматический доступ. Используйте для своих персонажей и личных копий, указывайте авторов при повторной публикации их работы и не нагружайте сайты.

## Приватность

- Данные отсканированных персонажей никогда не покидают браузер. Без аналитики, без внешнего кода.
- Специальные разрешения не нужны. Расширение работает только на страницах сайтов, которые вы открываете сами.
- Единственные сетевые вызовы — к сайту, на котором вы уже находитесь.

## Для разработчиков

Расширение — чистый JavaScript без зависимостей и без сборки. Правьте `src/` и перезагружайте со страницы расширений.

```sh
node --test
```

`src/scraper.js` читает JanitorAI, `src/emochi.js` — Emochi, `src/polybuzz.js` — Polybuzz, `src/cai.js` — Character.ai, `src/crushon.js` — Crushon.ai. Все пять заполняют одну форму карточки, поэтому экспортёры и панель никогда не знают, на каком вы сайте. `src/exporters.js` преобразует, `src/panel.js` и `src/panel.css` — панель на странице, `background.js` — service worker для запросов, которые content script сделать не может (CORS, запрещённые заголовки).

Два файла существуют только для сайтов, которые никогда не публикуют запись через API: `src/intercept.js` работает в мире самой страницы (`world: "MAIN"`, `document_start`) и копирует в DOM то, что страница уже знает; `src/harvest.js` собирает эти нагрузки и оценивает каждый объект против списка известных имён полей. Третий закрытый сайт стоит одного файла, где объявлены его ключи.

**Запись API по сайтам находится в английском README** ([Developer reference](README.md#developer-reference-english-only)). Она намеренно остаётся на английском: это справочный материал и часть, которая быстрее всего устаревает при изменениях на сайте. Переведём, когда она стабилизируется.
